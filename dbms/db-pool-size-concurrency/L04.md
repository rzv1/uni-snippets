# L04: Optimizare a Performantei: EF Core & SQLite

## 1. Introducere
Acest raport detaliaza strategiile de optimizare implementate pentru imbunatatirea performantei accesului la date intr-o aplicatie .NET folosing Entity Framework si SQLite. Obiectivul principal a fost eliminarea blocajelor comune de I/O si reducerea latentei interogatilor.

---

## 2. Tehnici de Optimizare

### A. Eager Loading (N+1 query problem)
Problema N+1 apare atunci cand aplicatia executa o interogare initiala pentru a recupera o lista de obiecte (1), apoi executa interogari separate pentru fiecare obiect din acea lista pentru a-i incarca proprietatile (N)
* **Solutia:** Utilizarea metodei `.Include(c => c.Payments)`.
* **Efect:** EF Core genereaza un `JOIN` la nivel de SQL, aducand toate datele necesare intr-o singura adresare catre baza de date.

### B. Indexarea Bazei de Date
In lipsa crearii unor indecsi, SGBD-ul este nevoit sa scaneze fiecare rand dintr-un tabel pentru a gasi potriviri, denumit si Full Table Scan.
*   **Solutia:** Crearea de indecsi pe coloanele frecvent filtrate: `type`, `id_customer`, `amount`.
*   **Efect:**  Reduce complexitatea cautarii de la $O(N)$ la $O(logN)$.

### C. Bulk Operations
Actualizarea individuala a unui numar masiv de inregistrari este ineficienta din cauza apelurilor `SaveChanges()` multiple.
*   **Solutia:** Utilizarea `ExecuteUpdate()` (EF Core 7+).
*   **Efect:**  Executa o singura instructiune SQL `UPDATE`, evitand incarcarea entitatilor in memorie (urmarirea lor de catre Change Tracker).

### D. Compiled Queries
EF Core sufera de overhead pentru parsarea expresilor LINQ in SQL.
*   **Solutia:** `EF.CompileQuery(...)`.
*   **Efect:**  Pre-compileaza query-ul, fiind o varianta mai eficienta pentru un query executat frecvent in care se schimba doar parametrii.

## 3. Masuratori performanta

Rezultate pe baza testelor rulate pe date de referinta (14 clienti, 10.000 plati):

| Tehnica               | Cereri DB | Timp Executie |
|:----------------------|:---------------:|:------------------:|
| **N+1 (Standard)**    |       15        |      ~148 ms       |
| **Eager Loading**     |        1        |       ~15 ms       |
| **Fara Indecsi**      |        -        |      >200 ms       |
| **Cu Indecsi**        |        -        |       <10 ms       |
| **Update Individual** |      1000+      |      Secunde       |
| **ExecuteUpdate**     |        1        |       <50 ms       |

### Analiza Planului de Executie (EXPLAIN QUERY PLAN)
*   **Offset Paging:** Afiseaza `SCAN Table`, deci SQLite citeste paginile pana ajunge la offset-ul dorit $=>$ timpul de cautare creste liniar cu numarul paginii.
*   **Cursor Paging:** Afiseaza `SEARCH Table USING PRIMARY KEY`. Baza de date sare direct la locatia memoriei unde se afla cursorul $=>$ performanta este aceeasi indiferent de pagina cautata.

## 4. Compromisuri si Utilizare

### Eager Loading vs. Lazy Loading
* Eager Loading este de preferat in momentul in care exista certitudinea ca atributele elementelor cerute din baza de date vor fi accesate.
* In caz contrar, se foloseste lazy loading pentru a evita umplerea memoriei cu date irelevante.

### Indexare
*   Utilitate mare pe coloane folosite in `WHERE`, `JOIN` sau `ORDER BY`.
*   Incetineste operatiunile de `INSERT` si `UPDATE`, deoarece indecsii trebuie actualizati pe disc la fiecare modificare.

### Offset vs. Cursor Paging
*   **Offset:** Bun pentru UI-uri simple unde utilizatorul sare la pagini specifice (Ex: pagina 5).
*   **Cursor:** Esential pentru procesarea unei cantitati mari de date in timp scurt.

---

## 5. Chestii interesante invatate

1.  **Date > Intuitie:** Intuitia despre viteza unei interogari la baza de date nu va bate niciodata precizia utilizarii unui `Stopwatch` sau `EXPLAIN query plan`
2.  **Logging overhead:** Logging-ul excesiv in consola poate face o comanda rapida sa para lenta din cauza duratei scrierii in terminal.
3.  **Viteza variabila:** Folosirea metodei `.AsEnumerable()` poate ingreuna artificial durata de executie a unui query prin faptul ca tot ce se executa in continuarea ei nu mai tine de baza de date, si de procesorul pe care ruleaza aplicatia.
